# СМЕНА 400

Интерактивный тренажёр принятия решений для проводников высокоскоростных
поездов. Работает локально, полностью — без внешних сервисов и без ключей.

> **Не угадай правильный ответ. Прими правильное решение.**
>
> Продукт не учит правильному ответу. Он учит видеть последствия решения —
> в том числе те, что приходят не сразу.

---

## Быстрый старт

```bash
cd smena400
npm install
npm run db:seed      # создаёт базу и проверяет, что все ситуации играбельны
npm run dev
```

Открыть <http://localhost:5173>.

Ничего настраивать не нужно: ни переменных окружения, ни ключей, ни внешних
сервисов. Логина тоже нет — игрок опознаётся анонимной кукой.

Требования: **Node.js 22.5 или новее** (используется встроенный `node:sqlite`)
и npm. Больше ничего.

### Готовая сборка

```bash
npm run build
npm start            # http://localhost:5400 — и API, и клиент
```

## Что здесь происходит

Проводник открывает ситуацию, попадает в неё и принимает решения под
таймером. Каждое решение меняет две шкалы и открывает разные пути. Часть
последствий приходит сразу, часть — через несколько шагов, когда связь
с причиной уже не очевидна. В конце — разбор, который эту связь показывает,
и предложение пройти заново с другой стратегией.

```
ситуация → контекст → давление времени → решение → последствия →
новая информация → новое решение → итог → разбор → повторное прохождение
```

Повторное прохождение — не работа над ошибками, а основная механика:
именно сравнение двух попыток доказывает человеку, что результат зависел
от него.

## Три ситуации

Все три взяты из банка «Ситуации на борту». Ни одна не придумана.

| № в банке | Ситуация | Чему учит |
|---|---|---|
| **19** | Пассажиру стало плохо | Приоритизация под жёстким временем: окно на организацию встречи медиков закрывается по расписанию, а не по вашей готовности |
| **20** | Пассажир курит на борту, включая электронные | Деэскалация: требование одно и то же, но сказанное при всех и сказанное наедине разводят шкалы в разные стороны |
| **16** | Не работает розетка, мультимедиа или кнопка вызова | Расхождение шкал: пассажира можно полностью удовлетворить, не решив при этом главную проблему |

Подробный разбор выбора и проверка каждой по критериям —
[`docs/SOURCES.md`](docs/SOURCES.md), раздел 3.

## Откуда взят материал и чего в нём нет

Это важнее, чем кажется, поэтому вынесено в начало.

В рабочем каталоге проекта есть только **конспект** нормативных документов
внутри `Смена_400_описание продукта.docx`. Полных текстов 974-р, 989-р, 990-р
и самого банка «Ситуации на борту» с рекомендуемыми реакциями **нет**.

Отсюда три жёстких правила, которые проверяет валидатор:

1. **Ни одной ссылки на пункт стандарта.** Мы не видели текста и не имеем
   права ссылаться на «п. 5.3.2». Валидатор отклоняет такой сценарий.
2. **`normative_rule` — только подтверждённое.** Если источник о чём-то
   молчит, молчит и продукт.
3. **`gameplay_interpretation` — отдельно и явно.** Всё, что придумали мы
   (пороги, величины шкал, порядок действий, сроки), названо своим именем
   в паспорте каждой ситуации и показано пользователю в интерфейсе.

Практический пример: в сценарии про медицинский инцидент **нет медицинских
манипуляций**. Проводник наблюдает, докладывает и организует помощь. Порядок
оказания первой помощи в доступных материалах не описан — значит, выдумывать
его продукт не имеет права.

Полная карта источников: [`docs/SOURCES.md`](docs/SOURCES.md).

> **Что снимет это ограничение:** полные тексты трёх стандартов и банк
> ситуаций с рекомендуемыми реакциями. После этого `normative_rule`
> и `source_reference` уточняются правкой JSON — без единой строчки кода.

## Архитектура

```
engine/      Scenario Engine — чистые функции, ни HTTP, ни базы, ни React
  model.js     две шкалы, пять компетенций, типы взаимодействия
  machine.js   состояния, действия, эффекты, таймер, отложенные последствия
  intent.js    детерминированный разбор свободной реплики
  feedback.js  правила разбора и сравнение попыток
  validate.js  проверка сценария и дисциплины источников

content/     Конфигурация, а не код
  situations.json       инвентаризация банка ситуаций
  scenarios/*.json      паспорта сценариев

server/      HTTP и хранилище
  index.js     маршруты
  lib/db.js    SQLite (встроенный node:sqlite)
  lib/content.js  загрузка сценариев и сборка того, что видит клиент
  lib/ai.js    опциональный AI-слой

src/         Клиент (React + TypeScript + Tailwind)
tests/       Тесты ядра, контента и сквозной тест API
tools/        Валидатор, подготовка базы, запуск разработки
```

### Три правила, на которых всё держится

**1. Движок ничего не придумывает.** Эффекты берутся строго из описанного
перехода конкретного сценария. Универсальной формулы «хороший ответ = +10»
в коде не существует — её отсутствие проверяется тестом.

**2. Допустимость решает сервер.** Клиент присылает намерение, а не результат.
Знание идентификатора действия не даёт возможности его выполнить, если оно
недоступно в текущем состоянии, заблокировано флагом или требует
отсутствующего в вагоне ресурса.

**3. Граф не уходит на клиент.** Клиент получает текущее состояние и список
доступных сейчас действий — без переходов, эффектов и будущих состояний.
Иначе все ветки и финалы были бы видны в исходниках страницы, а отложенное
последствие, которое можно прочитать заранее, перестаёт быть последствием.

### Стек и почему такой

Задание предлагало Next.js + Prisma. Взят более простой набор, и раздел 21
задания это прямо допускает:

| Слой | Решение | Почему |
|---|---|---|
| Клиент | React 18 + TypeScript + Vite + Tailwind | Приложение полностью клиентское, SSR нечего давать |
| Сервер | Node stdlib `http` | Десяток маршрутов; фреймворк добавил бы зависимость и ничего не упростил |
| База | встроенный `node:sqlite` | Без нативной сборки и без шага генерации схемы; `npm install` предсказуем |
| ORM | нет | Три таблицы и десяток запросов — их видно глазами |

Побочный эффект: установка не тянет ни одной тяжёлой зависимости, а стенд
поднимается на любой машине с Node 22.5+.

## Формат сценария

Новая ситуация добавляется **файлом**, без изменений в движке.

```jsonc
{
  "schema": "smena400/scenario@1",
  "id": "sit-19-medical",
  "title": "Пассажиру стало плохо",

  "source": {
    "document": "Банк «Ситуации на борту»",
    "situation": "№19 — пассажиру стало плохо",
    "source_reference": "…откуда это известно…",
    "normative_rule": ["…что прямо следует из источника…"],
    "gameplay_interpretation": ["…что придумали мы…"],
    "scenario_rationale": "…зачем ситуация в тренажёре…"
  },

  "context": {
    "trip_stage": "движение",
    "service_class": "комфорт",
    "available_resources": ["связь с начальником поезда", "аптечка"]
  },

  "initial_state": { "loyalty": 60, "safety": 85, "flags": [] },
  "entry": "s-alarm",

  "states": {
    "s-alarm": {
      "kind": "decision",
      "text": "Девушка, скорее! Мужчине рядом плохо…",
      "timer_sec": 25,
      "free_text": true,
      "actions": [
        {
          "id": "a-report",
          "label": "Нажать кнопку связи и доложить начальнику поезда",
          "kind": "escalate",
          "key": true,
          "requires_resource": "связь с начальником поезда",
          "normative": true,
          "normative_ref": 0,
          "keywords": ["доложить", "связь", "лнп", "медики"],
          "patterns": ["(долож|сообщ).{0,25}(начальник|лнп)"],
          "effects": { "safety": 8, "loyalty": 0 },
          "competency": { "safety": 3, "communication": 3 },
          "set_flags": ["reported_early"],
          "consequence": "Доклад ушёл в первые секунды…",
          "alt_hint": "…как это выглядит со стороны другого решения…",
          "next": "s-lnp"
        }
      ],
      "on_timeout": { "effects": { "safety": -9 }, "next": "s-drift" }
    },
    "f-good": { "kind": "final", "verdict": "good", "text": "…", "summary": "…" }
  },

  "feedback_rules": [
    { "kind": "improvement", "when_flag": "window_missed", "text": "…" }
  ]
}
```

Ключевые возможности формата:

| Поле | Что даёт |
|---|---|
| `requires_resource` | Действие не предлагается, если ресурса нет в вагоне |
| `deferred` | Последствие срабатывает через N шагов — механика отложенной расплаты |
| `cancel_deferred` | Игрок успел исправиться, и последствие снимается |
| `next_when` | Один и тот же выбор ведёт в разные состояния в зависимости от флагов |
| `on_enter` | Событие при входе в состояние, условное по флагам |
| `kind: "sequence"` | Порядок действий; оценивается прежде всего то, что сделано первым |
| `on_timeout` | Бездействие как полноценный исход со своими эффектами |
| `key` | Решение попадёт в разбор вместе с альтернативной веткой |

Проверить банк: `npm run validate`.

## Свободная речь без обязательного AI

На части состояний можно отвечать своими словами. Человеку **не нужно**
знать идентификаторы, ключевые слова или формат команд — он пишет так, как
сказал бы вслух.

Разбор идёт в четыре шага, и все они детерминированные:

1. нормализация и приведение слов к основам;
2. регулярные выражения для очевидных намерений;
3. взвешивание по редкости слова **внутри этого состояния** — слово, которое
   есть у всех вариантов, не различает ничего;
4. порог уверенности и зазор до второго варианта.

Не уверены — не угадываем: пассажир переспрашивает, и ситуация не сдвигается.

Если подключён AI, при неуверенном результате спрашивается модель — но она
возвращает только идентификатор из уже разрешённого списка, и этот кандидат
проходит те же проверки движком. **Без ключа режим работает полностью.**

## AI-слой: опционально и бесправно

```bash
AI_PROVIDER=openai
AI_API_KEY=sk-...
AI_MODEL=gpt-4o-mini
AI_BASE_URL=https://api.openai.com/v1   # или свой совместимый шлюз
```

| | Без ключа | С ключом |
|---|---|---|
| Прохождение ситуаций | полностью | полностью |
| Свободная речь | собственный анализатор | + запасной разбор моделью |
| Реплики пассажира | из сценария | переформулированные, смысл и факты те же |
| Шкалы, переходы, допустимость | движок | **движок** |

Модель не может изменить состояние, создать переход, изменить шкалы,
обойти ограничение по ресурсу или определить нормативную правильность.
Единственное, что она может вернуть, — идентификатор из списка, который
мы ей дали; любой другой ответ отбрасывается.

Ключ читает только сервер. В браузер он не попадает никогда.

## Проверки

```bash
npm run validate     # банк ситуаций: связность, тупики, дисциплина источников
npm test             # 42 теста: ядро и контент
npm run test:api     # сквозной тест против живого сервера
npm run test:browser # прохождение руками в настоящем браузере (нужен Chrome)
npm run typecheck    # строгий TypeScript
npm run check        # validate + test + typecheck
```

`npm run test:api` поднимает собственный сервер на отдельном порту
и отдельной базе, поэтому ничего не портит. Полный прогон включает реальное
ожидание таймера (~25 с); пропустить — `FAST=1 npm run test:api`.

Что проверяется по существу:

- случайные прохождения каждой ситуации **никогда** не попадают в тупик;
- разные стратегии дают разные финалы и разные шкалы;
- в каждой ситуации есть решение, разводящее шкалы в противоположные стороны;
- отложенное последствие действительно срабатывает;
- запрещённое действие не проходит через HTTP даже с известным идентификатором;
- чужую сессию нельзя открыть;
- опоздавшее действие превращается в бездействие, а досрочно объявить
  истечение таймера нельзя;
- ни один сценарий не ссылается на пункт стандарта;
- разбор нигде не говорит «правильный ответ».

## API

Полная спецификация — [`openapi.yaml`](openapi.yaml).

| Метод | Назначение |
|---|---|
| `GET /api/meta` | шкалы, компетенции, состояние AI-слоя |
| `GET /api/scenarios` · `GET /api/scenarios/:id` | список и паспорт ситуации (без графа) |
| `POST /api/sessions` | начать прохождение |
| `GET /api/sessions/:id` | текущий экран |
| `POST /api/sessions/:id/actions` | ход: выбор, порядок или бездействие |
| `POST /api/sessions/:id/message` | свободная реплика |
| `POST /api/sessions/:id/finish` | прервать прохождение |
| `GET /api/sessions/:id/debrief` | разбор и сравнение с прошлой попыткой |
| `GET /api/progress` | прогресс игрока |

Отказ движка — штатный ответ `409` с кодом (`not-allowed`, `not-expired`,
`unclear`, `no-free-text`, `finished`), а не ошибка сервера.

## Что осознанно не сделано

- **Нет «Смены» как последовательности ситуаций.** Архитектура это допускает:
  состояние сессии уже содержит шкалы и флаги, а сцепить ситуации — вопрос
  оболочки над движком, а не его переписывания. В MVP приоритет отдан
  качеству трёх ситуаций.
- **Нет админ-панели.** Сценарии — конфигурация; новая ситуация добавляется
  файлом и проверяется валидатором. Раздел 26 задания прямо это разрешает.
- **Нет ролей, LMS, лидерборда и сложной авторизации.** Раздел 27 запрещает
  их прямым текстом, и это правильный запрет: они забирают внимание
  у продуктовой петли.
- **Нет голосового ввода.** Свободная речь набирается текстом. Для
  анализатора это ничего не меняет — он получит ту же строку.
- **Нет изображений вагонов и интерьеров.** В материалах проекта их нет,
  а случайные стоковые фотографии хуже, чем честная типографика.
